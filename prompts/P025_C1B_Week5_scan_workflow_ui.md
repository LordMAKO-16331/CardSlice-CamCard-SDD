# P025-C1B — Week 5：名片扫描流程分阶段 UI 重构

## 一、项目背景

CamCard SDD iOS 课程项目当前处于 Week 5 UI 收尾阶段。

已完成：

- 相册导入。
- Single 系统相机入口。
- 自动检测名片边界。
- 手动四角调整及无候选时手动裁剪。
- 透视校正。
- 中英文 OCR。
- 联系人结构化解析。
- 人工确认。
- SwiftData 保存。
- 名片管理及导出。

P025-C1A 已经通过用户手动功能验证及全部 Xcode 回归测试。

当前问题：

CardImageImportView 仍采用开发测试时期的长页面，图片处理、裁剪、OCR、解析和保存功能分散在多个折叠区域中。

虽然按钮都能使用，但操作流程不符合正常 iOS 用户习惯。

本轮只重构扫描流程的 UI 组织及必要状态导航。

不重写现有图像处理与识别算法。

## 四、设计目标

将扫描流程整理成明确的分阶段交互：

选择来源\
→ 裁剪校正\
→ 自动识别\
→ 人工确认\
→ 保存完成

各阶段应有清晰的主操作。

用户不需要理解程序内部的 Vision、OCR、Parser 或 CoreImage 执行步骤。

不得将所有阶段的主要操作同时堆在一个可滚动长页面中。

不强制每个阶段使用独立 Swift 文件，但必须有明确的阶段状态和 UI 展示边界。

## 五、阶段一：选择图片来源

进入扫描功能后：

1. 清晰展示「拍摄名片」与「从相册导入」入口。
2. 相册导入后自动进入裁剪校正阶段。
3. 系统相机拍摄成功后进入同一裁剪校正阶段。
4. 取消相册选择时安全停留或返回。
5. 相机权限拒绝、相机不可用时保留现有错误提示。
6. 不因模拟器无法实际拍照而阻塞相册流程。
7. 不显示无关的开发调试按钮。

不得重新实现相机权限管理。

## 六、阶段二：裁剪与校正

这是本轮 UI 重构的重点。

要求：

1. 页面主要区域用于展示当前名片图片。
2. 图片上显示已检测到的裁剪四边形。
3. 用户可以直接拖动裁剪边界。
4. 存在多个自动候选时仍可切换。
5. 自动检测失败时仍可手动建立裁剪区域。
6. 保留恢复边界的能力。
7. 提供明确的主操作「确认裁剪」。
8. 用户不需要额外寻找单独的透视校正按钮。
9. 点击确认后，使用最终四边形执行现有透视校正。
10. 进入下一阶段前，确保裁剪结果有效。
11. 可以返回重新选择图片或重拍。
12. 返回、重选、重拍时不得沿用上一张图片的裁剪状态。

必须保留 P025-C1A 已验证的全部手动裁剪能力。

不得修改裁剪几何算法及透视服务接口。

## 七、阶段三：OCR 与字段解析

确认裁剪后，自动衔接现有 OCR 与字段解析流程。

要求：

1. 用户不需要分别点击「开始 OCR」和「解析字段」。
2. 明确展示正在识别的状态。
3. OCR 成功后执行原有字段解析。
4. 保留原始 OCR 文本。
5. 保留字段解析结果、未分类信息及歧义信息。
6. 识别与解析完成后进入人工确认。
7. OCR 无结果时展示可理解的提示。
8. 失败时提供重新识别或返回裁剪的方式。
9. 不允许失败后直接生成虚构联系人信息。
10. 不允许旧图片的异步结果覆盖新图片。
11. 防止重复触发 OCR 造成并发结果错乱。
12. 关闭扫描流程后，过期任务不得再次推进界面或写入数据。

可保留 OCR 原文查看入口，但不要求在正常流程中默认展开技术调试信息。

不得重新编写 OCR 或 Parser。

## 八、阶段四：人工确认

识别完成后进入字段确认阶段。

要求：

1. 复用现有 CardFieldCorrectionView。
2. 可以查看、修改姓名、公司、职位、联系方式等字段。
3. 电话、邮箱继续支持动态新增和删除。
4. OCR 原始结果与用户最终确认值保持区分。
5. 用户确认后才允许进入保存操作。
6. 用户取消人工确认时不得直接写入数据库。
7. 返回重新裁剪后，旧确认结果必须正确失效。
8. 不得自动跳过人工确认。
9. 校验失败时保留草稿供用户修改。
10. 不得损坏已完成的保存名片编辑流程。

人工确认页面与已保存名片的再次编辑虽然复用组件，但保存时机不同，必须保持原有差异。

## 九、阶段五：保存与完成

人工确认后使用现有记录组装及 Repository。

要求：

1. 继续保存原图和处理图。
2. 保存 OCR Raw Text。
3. 保存初始 Parsed Fields。
4. 保存最终人工确认字段。
5. 保存成功后提供清晰的完成反馈。
6. 根据现有导航机制返回名片夹，并刷新列表。
7. 保存失败时保留可恢复的会话数据。
8. 禁止重复点击导致重复保存。
9. 用户在保存前退出不得产生不完整名片。
10. 不得为了实现导航而修改 SwiftData Schema。

不重新实现 Repository 或记录组装逻辑。

## 十、导航和状态原则

本轮必须特别注意：

1. 当前阶段应有清晰的页面标题。
2. 主操作按钮应明显且容易点击。
3. 不依赖长距离滚动寻找下一阶段。
4. 返回与取消必须有明确语义。
5. 用户更换图片后，旧 OCR、解析和确认结果全部失效。
6. 旧异步任务不得覆盖当前阶段。
7. 处理中避免重复提交同一任务。
8. 失败时允许重试。
9. 关闭会话不污染已经保存的名片。
10. 不增加不必要的复杂动画。
11. 尽量使用标准 SwiftUI 导航、按钮和状态展示。
12. 原有 DEBUG 工具不得出现在正常用户操作主路径中，但不要直接删除开发调试能力。

建议使用明确的扫描阶段状态，而不是多个互相矛盾的 Boolean 拼接流程。

状态设计必须与现有代码兼容，避免形成第二套重复状态来源。

## 十二、自动化测试

优先测试阶段状态转换及数据隔离，不为纯视觉变化编写大量重复测试。

重点覆盖：

1. 选图成功进入裁剪阶段。
2. 取消选图不进入识别。
3. 确认裁剪后进入识别阶段。
4. 裁剪失败不进入下一阶段。
5. OCR 成功后进入人工确认。
6. OCR 失败后可以重试。
7. 更换图片后旧任务结果失效。
8. 返回裁剪后旧解析和确认结果不继续使用。
9. 取消人工确认不写入数据库。
10. 保存成功只生成一条记录。
11. 保存失败后仍可恢复。
12. 原有相册导入、手动裁剪、OCR、人工确认及持久化测试保持有效。

保留全部已有测试和断言。
